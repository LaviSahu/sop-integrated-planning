# Data Dictionary

All of `data/families.json` and `data/resources.json` are generated by
`datagen.py` (seed `20260714`) and committed to the repo — re-running
`datagen.write_data()` reproduces them byte-for-byte. Every field below
is a real dataclass field in `models.py`, not a documentation gloss.

## `data/families.json` — one object per product family

| Field | Type | Source constant | Meaning |
|---|---|---|---|
| `id` | string | `FAMILY_TABLE` | Stable family code, e.g. `FAM-REF`. |
| `name` | string | `FAMILY_TABLE` | Display name, e.g. `Refrigerators`. |
| `unit_price` | float | `FAMILY_TABLE` | List price per unit, USD. |
| `unit_variable_cost` | float | `FAMILY_TABLE` | Variable cost per unit, USD. |
| `opening_inventory_units` | float | `FAMILY_TABLE` | Units on hand at the start of January — the only month with nonzero opening inventory sourced from outside the model; every later month's opening inventory is the prior month's `ending_inventory_units`. |
| `base_monthly_demand` | list[float], length 12 | `_monthly_base_demand()` | Unconstrained monthly demand (units), index 0 = January … index 11 = December. Seasonality-shaped (`SEASONAL_SHAPE`, normalized to average 1.0) times the family's stated average monthly demand, times a ±3% seeded jitter (`_NOISE_PCT`), floored at 0. |
| `upside_uplift_pct` | float | `FAMILY_TABLE` | Fractional demand uplift applied on top of `base_monthly_demand` for the UPSIDE and CONSTRAINED scenarios only (`demand.py`'s `UPLIFT_SCENARIOS`). `0.0` for families with no upside play (Microwaves, Ranges). |
| `resource_hours_per_unit` | dict[str, float] | `HOURS_PER_UNIT` | Resource id → hours consumed per unit produced. A resource absent from this dict is not used by the family (treated as 0.0 everywhere downstream). |
| `unit_margin` *(computed, not stored)* | float | `Family.unit_margin` property | `round(unit_price - unit_variable_cost, 4)`. Not a JSON field in the dataclass — `jsonable()` injects it into every serialized `Family` (see `models.jsonable`) so it's visible in `data/families.json` and the dashboard without being a second source of truth to keep in sync. |

### The six families (seeded values)

| id | name | unit_price | unit_variable_cost | unit_margin | opening_inventory_units | avg monthly demand | upside_uplift_pct |
|---|---|---|---|---|---|---|---|
| FAM-REF | Refrigerators | $1,349.00 | $812.00 | $537.00 | 4,200 | 3,000 | 25% |
| FAM-WSH | Washers | $799.00 | $471.00 | $328.00 | 3,100 | 2,500 | 20% |
| FAM-DRY | Dryers | $699.00 | $402.00 | $297.00 | 2,600 | 2,000 | 15% |
| FAM-MWV | Microwaves | $179.00 | $96.00 | $83.00 | 6,500 | 4,000 | 0% |
| FAM-DSH | Dishwashers | $649.00 | $381.00 | $268.00 | 2,200 | 1,800 | 10% |
| FAM-RNG | Ranges | $899.00 | $549.00 | $350.00 | 1,900 | 1,500 | 0% |

"avg monthly demand" is the `FAMILY_TABLE` input to the seasonality
curve, not a stored field — actual `base_monthly_demand` values vary
month to month around it.

## `data/resources.json` — one object per shared production resource

| Field | Type | Source constant | Meaning |
|---|---|---|---|
| `id` | string | `RESOURCE_TABLE` | Stable resource code, e.g. `RES-LINEA`. |
| `name` | string | `RESOURCE_TABLE` | Display name, e.g. `Assembly Line A (heavy)`. |
| `monthly_available_hours` | float | `RESOURCE_TABLE` | **Installed** capacity — the number every RCCP utilization figure is measured against, in every scenario (`capacity.compute_loads`). Does not change with scenario; only `constrain.effective_capacity_hours` decides whether a scenario assumes an investment beyond it. |

### The four resources (seeded values)

| id | name | monthly_available_hours |
|---|---|---|
| RES-LINEA | Assembly Line A (heavy) | 9,500 |
| RES-LINEB | Assembly Line B (light) | 7,800 |
| RES-QA | Test / QA | 2,220 |
| RES-PKG | Packaging | 1,600 |

Refrigerators, Washers, and Dryers — the three families carrying a
nonzero `upside_uplift_pct` — are the heavy users of Assembly Line A
(`RES-LINEA`); Microwaves, Dishwashers, and Ranges run on the lighter
Line B. This is why Line A, not Line B, is the resource that clears
100% utilization once the upside overlay is added (see
[KPI Reference](03-kpi-reference.md) and
[Scenario Guide](05-scenario-guide.md)).

## Downstream dataclasses (computed, not stored as JSON inputs)

These aren't in `data/*.json` — they're computed per scenario at
runtime and only reach disk in `output/comparison.json` (gitignored,
regenerated by `make demo`). Listed here because they're the shape
every module downstream of `datagen.py` actually works with.

| Dataclass | Module | Fields |
|---|---|---|
| `DemandLine` | `demand.py` | `scenario`, `family_id`, `month` (1-12), `demand_units` |
| `ResourceLoad` | `capacity.py` | `scenario`, `resource_id`, `month`, `load_hours`, `available_hours`, `utilization_pct`, `is_bottleneck` |
| `SupplyLine` | `constrain.py` | `scenario`, `family_id`, `month`, `demand_units`, `produced_units`, `opening_inventory_units`, `shipped_units`, `unmet_units`, `ending_inventory_units`, `fill_rate` |
| `FinanceLine` | `finance.py` | `scenario`, `family_id`, `month`, `revenue`, `gross_margin`, `lost_revenue`, `lost_margin`, `inventory_value` |
| `FinanceSummary` | `finance.py` | `scenario`, `total_revenue`, `total_gross_margin`, `total_lost_revenue`, `total_lost_margin`, `ending_inventory_value`, `fill_rate` |
| `Kpi` | `kpi.py` | `key`, `label`, `value`, `unit`, `context` |

> `gross_margin` / `total_gross_margin` are legacy internal field names
> meaning **contribution margin** (`shipped × (price − variable cost)`).
> True gross margin would subtract allocated fixed overhead, which this
> model deliberately does not allocate.
